## 表单到登录

RHF 收集字段，Zod resolver 校验；只有通过后才调用 API。提交中按钮禁用，失败保留输入。登录响应必须同时包含 userId/accessToken/refreshToken 才建立完整会话；userId 不转 Number。

```text
有效表单 -> Login -> 检查业务体 -> 解析三项会话
 -> session.set -> 通知订阅 -> 清旧身份缓存 -> 安全 redirect
```

redirect 只能回站内安全相对路径，拒绝 //evil 和外部协议。前端校验跳转地址是防开放重定向，不是替后端校验身份。

## 两个 Token 为什么都发

当前后端同时读取 Authorization 与 Refresh-Token，二者都使用 Bearer。不是常见“access 失败就随便请求刷新 endpoint”的模板，不能复制别的项目鉴权流程。

client 只识别稳定业务码 3005 且带 metadata.access_token 的分支。更新 accessToken 后原请求最多重发一次；没有新 token、普通 401/403、网络失败都不能进入循环。测试用假的 token 字符串，不包含真实凭据。

## 并发与退出

错误码集中放在 [error-codes.ts](../../src/lib/api/error-codes.ts)。后端规范化后，服务层“请先登录”可能返回 3124/3127/3128/3129，不能只检查 HTTP 状态。3123 和 3129 的 reason 都可能是 INVALID_USER_ID，但前者是参数错误，后者才是身份错误。因此会话失效按精确数字码分类；业务部分成功和冲突仍使用后端明确保留的 reason 与 metadata。新增业务码时先确认含义，不能把整个数值区间或创建 token 的内部错误都加入退出名单。

后端只缓存当前 accessToken，同标签页受保护请求串行，避免多个旧请求竞争刷新。这样慢文件请求会延迟其他请求，是明确的首版取舍。不能推导为跨标签页、跨设备竞争已解决。

session.generation 在登录/退出时增加。请求记住发出时世代，返回时不匹配就拒绝接受；refresh 仅在期望世代一致时写入。否则退出后的旧刷新响应可能把用户重新“登录”。

main 订阅身份变化，取消 Query 并清缓存。sessionStorage 只支持当前标签页刷新；关闭标签页后不当作长期登录。恶意同源脚本仍能读到 token，所以它不等于 HttpOnly Cookie。

## 注册与验证码边界

注册响应现在包含 userId 和双 token，复用登录会话校验；可选头像在注册成功后另传。注册部分成功时用 reason 和 metadata 区分并引导登录。图形验证码只有获取适配，没有假设后端在登录时验证了它。邮箱倒计时只是 UX，不是限流；后端必须自己限制发送。

修改密码成功清会话，再登录。匿名找回走 /forgot-password，验证码发送以 reset_password 用途提交，找回提交不携带已登录凭据。
