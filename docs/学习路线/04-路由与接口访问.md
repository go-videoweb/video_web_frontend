# 04 路由、API 层与服务端数据

状态：项目讲解已补充。目标是从 URL 跟踪到最终渲染。

## 先区分三个概念

Router 管理“在哪一页、参数是什么”；Query 管理“服务端数据是什么状态”；fetch 真正发送 HTTP。它们不是三个替代框架，而是不同职责。用户提交命令用 mutation，即使后端用了 GET。

## 用列表串起来

```text
/?category=科技&page=2
 -> 路由校验 search
 -> Discover useSearch
 -> Query key 包含 userId/category/page
 -> getVideos(category,page,signal)
 -> request('/video/list?...')
 -> JSON 业务错误检查
 -> Zod 解析 -> video-card 列表
```

URL 参数不可信，需要处理负页码、无效分类。后端资源 ID 也不应该拿来做任意字符串插值；positiveId 在边界拒绝无效值。

queryFn 接收 signal，传到 fetch。离开页面/清缓存可以取消读取，但已经在服务器执行的写操作不能靠浏览器 abort 回滚。

## Query key 是数据身份

['videos', userId, category, page] 中任何一项变化都可能对应不同数据。漏掉用户 ID 会让登录切换复用私人缓存；漏掉页码会让不同页互相覆盖。useQuery 的 isPending/isError/data 对应界面加载、失败、成功分支，不用自己复制一组布尔状态。

invalidateQueries 不是修改服务器，而是把匹配缓存标为失效，活跃订阅可重新获取。范围太大可能重复请求有副作用的详情，因此评论提交只失效评论/回复，不整站刷新。

## 请求的成功有两层

HTTP 200 并不保证业务成功。网关可能返回 {code,reason,message} 或嵌套 resp/common 的失败码。client 统一识别，再抛 ApiError。验证码响应里的字符串 code 不是数字业务错误，不能只看字段名。

未知网络结果与明确失败不同。例如请求已到服务器但响应丢失，重复创建元信息可能产生两条记录。客户端不自动重试普通写命令；只有后端明确保证尚未执行业务的 token 刷新分支可重发一次。

## 契约不是运行时护身符

backend.openapi.yaml 是来源快照；effective.openapi.json 修正已核对的文件/multipart 描述；generated.d.ts 是类型参考。schema.parse 负责实际输入验证。更新快照后运行 api:generate，CI 的 api:check 只检测仓库内产物是否一致，不会自动访问兄弟后端/线上网关。

路由生成文件与 API 类型文件都不手改。新增接口先修改源契约/脚本，再运行生成。

## 可选练习

在浏览器 Network 找到列表请求，核对 page_num=2 与 class 的编码。用错误页面参数打开首页，观察校验后的回退，不修改 HTTP 业务。运行 pnpm api:check、pnpm typecheck。不要把 apiBase 改成含密码的 URL。
