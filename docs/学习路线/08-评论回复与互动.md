## 评论流程

登录后读取根评论，排序为 created_at 或 cnt_upvote。作者资料通过 ['user',publisherId] 缓存补全，同一作者不会因每条评论重复建立一份状态。昵称不可用时显示稳定 ID 尾部，不能捏造姓名。

```text
输入 -> trim/长度限制 -> 点击发布 -> postComment
 -> 成功清草稿 -> 评论/回复 key 失效 -> 重新读
 -> 失败保留内容并显示说明
```

评论表单的内容属于局部 state，列表来自 Query。Mutation isPending 禁用提交按钮，防止正常连击；不是幂等保障。服务端仍应根据业务防重。

根评论 parentId='-1'，回复使用直接对象 ID。只有展开楼层才独立分页；主列表与展开楼层各按 hasMore/nextCursor 续查，刷新和排序切换不会拼接旧游标。

## 为什么不用通用乐观更新

视频详情返回个人状态，null 不等于未点赞。整视频点赞仍是切换，未知结果时需显式核对；评论和弹幕使用 liked 布尔值提交目标状态，并以响应的状态与计数更新。

贝壳选择 1/2 个并提交，成功消息不代表本地计算的新余额。精确余额需要服务端回读；不要只减数字制造事务完成假象。

## 分享与弹幕

分享 GET 会记录行为，放在 mutation，不做页面预取。前端使用服务端返回的 URL；剪贴板失败仍展示可选中的链接，不再次调用分享。

弹幕发送包含正文、整数秒与颜色，独立按播放区间读回，区间内游标保留零秒和真实 ID。

## 会话与错误

评论读取也要登录；游客仍可看公开详情和播放器，评论区给登录入口。API 层处理两种 token 与业务码。评论作者查询失败不应该吞掉整条评论内容。

发布网络失败时保留输入，但用户重试前应考虑“服务端已成功、响应丢失”的未知结果；自动 retry=false 不能解决服务端幂等，只能避免放大风险。

## 可选练习

在演示发一条根评论，再回复并展开，检查内容可回读。刷新后模拟写入会清空，这是演示内存的边界。读 E2E 中提交/回复断言，运行对应观看场景。

局部改动练习：调整评论时间与点赞的顺序，保留 aria-label、禁用状态和 stable key；不修改后端排序字段。
